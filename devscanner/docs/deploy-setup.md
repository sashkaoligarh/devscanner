# Project deployment setup

Open **Deploy Setup** from a project card. Choose a saved SSH server and a workflow target. The app can reconnect using the saved server credentials. Preparing a server installs packages and changes its configuration; it does not publish local repository changes or run GitHub workflows.

The **Deployment** tab contains the server, profile, workflow target and update options. **Environment** appears for server-pull deployments and supports local env import, key generation and filtering variables by name. **Advanced** contains the deploy account, remote directory, sudo, nginx, TLS and existing SSH key settings. Drafts are saved per project/server/workflow/profile and restored after closing the dialog or restarting the app. **Prepare server** stays visible below the scrolling form; all settings are locked during preparation.

The selected folder can contain categories at several levels, for example `projects/kr/kpcep` and `projects/ocp/strapi-astro-monolith`. The project view groups cards into collapsible folders with project counts. Folders start collapsed, and manually expanded folders are saved in settings. Open a category and click **Deploy** on the individual project card. **Deploy** uses that project's root, including its workflow and deployment files; frontend/backend components remain inside their monolith's card. Direct projects in the selected folder stay visible without an extra category. Search matches names, category paths and tech stacks and automatically expands matching folders. Favorites stay ordered within their folders.

A root manifest, Docker configuration, Git directory/worktree, workspace configuration, or `deploy/stack.yml` identifies a project boundary. Without these markers, a matching frontend/backend (or frontend/cms) pair is treated as an unversioned monolith; arbitrary sibling projects remain separate. Selecting a project root directly also keeps it as one card. Dependencies, build outputs and hidden tooling directories are skipped.

## Private network / VPN

Choose **Server pulls images**. The app detects `deploy/stack.yml`, `deploy/server.env.example`, a `deploy/*autodeploy*.sh` updater and `deploy/nginx.conf`. A Compose project without an updater gets a generated image-pull script.

1. Import a local env or fill the server environment fields. Required fields come from the updater's `required_vars` and Compose requirements. Template placeholders are not treated as credentials. For a new application, **Generate empty app keys** fills application keys and database passwords; provider credentials still come from their respective services.
2. Existing server env values are preserved. Enable **Replace existing server values** to apply non-empty form values over existing ones. Service-specific env names (for example `DATABASE_PASSWORD` → `POSTGRES_PASSWORD`) are mapped using Compose. Env values are never executed during local import and are safely quoted before the installed script sources them. They are not stored in application settings.
3. Enable nginx and set the public domain. Choose **No certificate — HTTP only**, an existing server certificate, manual PEM certificate/key installation, or Let’s Encrypt with automatic renewal. Certbot installs and issues the certificate during preparation; existing certificate files are not required for that mode.
4. Preparation checks/installs Docker Engine, Compose and runtime tools, creates the deploy account and installs its SSH key, installs the Compose file, updater, env and launcher, validates their syntax, and enables cron if selected. An existing project cron file from the previous setup layout is backed up when it points at the same updater. File replacement waits for the managed updater lock and the detected project updater lock. The generated cron runs as root and writes a private log in `<base>/run/autodeploy.log`.
5. Optionally run the first deployment. Otherwise the result states that preparation is complete and the first deployment was not run by the wizard. Cron may subsequently deploy published images.

For KPCEP, `KPCEP_BASE_DIR` follows the selected remote base, while digest-derived image references remain the updater's responsibility. Its GHCR API checks need `GHCR_USERNAME` and `GHCR_TOKEN` in server env; Docker Hub login cannot substitute for them. Existing script behavior, health checks, pinned digests and notifications remain intact. The launcher uses a separate release-state file and a configuration checksum so changes to Compose, env or the updater trigger a deployment even when image digests are unchanged.

Template values such as `replace_with_…`, `replace_key_…` and `github_pat_replace_me` count as missing and are excluded from env import. Required placeholders block preparation before remote writes. Real form/import values replace existing server placeholders without needing an overwrite override. **Generate empty app keys** also supports `IP_HASH_SECRET` and `FORM_CHALLENGE_SECRET`; provider credentials must be supplied separately. GHCR needs a [personal access token (classic) with read:packages and package access](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry#authenticating-with-a-personal-access-token-classic), including SSO authorization when required; fine-grained GHCR tokens are rejected during preflight.

For a plain Compose image-pull project, the result gives `sudo docker login` (or `sudo docker login ghcr.io`) because the scheduled updater runs as root. Compose must reference published images, not local builds. Relative bind mounts and `env_file` require an explicit deploy layout and are rejected before installation rather than silently omitted.

## Ports and TLS checks

In **Deployment → Ports and TLS**, click **Check server**. This reads listening TCP/UDP sockets with `ss` (iproute2), Docker published-port metadata and TLS file status through SSH/sudo, without installing or changing anything. Docker networks isolate container ports; [published host ports](https://docs.docker.com/engine/network/port-publishing/) must still be available on the host. NAT bindings are checked even when no docker-proxy socket appears in `ss`. An inspection failure blocks preparation rather than treating the server as empty.

Conflicting ports show the owning process/container. For server pull, choose **Use suggested ports** or enter a host port and **Check again**. Suggestions avoid occupied and planned ports, including nginx listeners. Only the installed Compose host bindings change; target ports, Docker-internal URLs and container health checks remain intact. Matching host nginx upstreams, updater HTTP health-check URLs and `*_HEALTHCHECK_URL` values in server env follow the chosen ports. Keep **Install nginx configuration** enabled when changing ports used by the detected nginx config. Choices are saved for the project/server/target and reused on future preparations; the local project files are unchanged.

Existing host nginx listeners may be shared by virtual hosts; another process or Docker container on the same listener is a conflict. Change a conflicting public listener in the nginx config, or resolve it in Servers before continuing. Current containers are recognized by their remote Compose file/directory; a different deployment using the same Compose project name is blocked to prevent one updater from replacing the other's containers. Use a unique `STACK_NAME`/Compose project name and remote base for separate deployments.

**Prepare server** always repeats inspection before remote writes. Ports are not reserved by the check, so another process can still occupy them afterward. Port ranges, host networking and unresolved port templates require explicit configuration before automatic checks can proceed. Direct GitHub deployments with a single inline Compose definition are inspected too, but their port changes must be made and committed in the Ansible playbook and nginx configuration: a server-only override would be overwritten by GitHub Actions. Unsupported playbook layouts are reported explicitly.

A TLS error names the actual certificate/key path and distinguishes missing, empty, unreadable files and failed sudo checks. **Configure TLS** opens **Advanced → TLS certificate and key**. Choose **Install certificate manually (PEM)** and paste a matching pair, keep an existing server certificate, or select **Let’s Encrypt — automatic renewal**. A failure during initial checks leaves the server unchanged and preserves form env values.

## Let’s Encrypt and renewal

For a project behind NAT, select **No certificate — HTTP only** to prepare nginx without certificate checks, issuance or renewal. The wizard converts the HTTPS app server to HTTP, removes redirect stubs, TLS directives and HSTS, and preserves application routes, upstreams and limits. Separate HTTP application routes are not silently discarded; an ambiguous config requires a combined HTTP config in Advanced.

For a single nginx site, leave **Domain or server IP** empty to use the saved SSH server address (including VPN/LAN IP), or enter the hostname you can reach. nginx accepts this host, and matching same-site HTTPS URLs in nginx/CORS and URL/origin env values use its HTTP address. Other external HTTPS services and credentials remain unchanged. This explicit HTTP selection also updates matching existing server env values; other env values retain the usual preservation behavior.

The local project config remains unchanged. Later, install a certificate manually in Nginx Manager or select manual PEM / Certbot in this wizard. Set public URL/CORS env values to the intended HTTPS origin when enabling TLS.

Select **Let’s Encrypt — automatic renewal**, provide the account email and accept the subscriber agreement. Public A/AAAA records for every `server_name` must route to this server, with inbound TCP port 80 reachable. SSH access through a VPN is fine when public HTTP is forwarded correctly. VPN-only domains and wildcard certificates require a manually supplied certificate; this wizard uses [HTTP-01 validation](https://letsencrypt.org/docs/challenge-types/#http-01-challenge), not a DNS provider integration.

Preparation installs nginx/Certbot when absent, configures an HTTP challenge webroot, obtains a project-specific certificate, then installs the full HTTPS config with its routes and upstreams. Existing certificates can be reused. The HTTP challenge location remains available for renewal, including when the site redirects other requests to HTTPS. New HTTP-only project configs can be converted to HTTPS for manual PEM or Certbot installation.

A dedicated systemd timer checks twice daily with randomized delay, and a successful renewal runs `nginx -t` followed by reload. Preparation runs a scoped `certbot renew --dry-run --no-random-sleep-on-renew` and verifies the timer before reporting success. A remote process deadline expires before the SSH deadline, so the test is stopped before rolling back its challenge route. The certificate name and timer are isolated by project/base/domain. On issuance, validation or renewal-test failure, the previous nginx site is restored and reloaded; a previously enabled managed timer is restored too. Completed earlier setup steps remain listed. Renewal follows Certbot’s [webroot and deploy-hook workflow](https://eff-certbot.readthedocs.io/en/stable/using.html#renewing-certificates).

Issuance and renewal failures show Certbot’s actual output with known credentials removed, plus hints for DNS, connection, HTTP challenge, account, CAA and rate-limit errors. The wizard reports whether rollback completed and preserves the original Certbot error if restoration also fails. A connection timeout to a public address while nginx answers on a private address requires checking the external firewall/NAT/proxy route to port 80. On a shared public address, route this domain’s challenge requests to its server through the existing proxy rather than replacing other projects’ forwarding rules.

## Codex deployment assistant

Open the **Codex** tab or **Ask Codex** after an error. The pinned `@openai/codex-sdk` runs in Electron’s main process; its native CLI is packaged outside ASAR. The assistant uses the existing local Codex login by default. **Codex connection** also accepts an optional model and OpenAI API key; keys use Electron safeStorage and only their presence is returned to the renderer. Every diagnosis uses a temporary isolated Codex home, sharing only the existing `auth.json` file through a link so token refreshes remain synchronized. Personal settings, MCP servers and plugins are not imported. Keyring-only logins require an API key or a local file-based Codex login. Authentication and usage follow [Codex’s authentication modes](https://learn.chatgpt.com/docs/auth).

The assistant receives the current error, preflight, relevant project configs with environment blocks/known credentials removed, and recent diagnoses for that project/server/target. It can request additional read-only nginx, Docker, Certbot, system or project-log diagnostics. The SDK runs without shell, personal MCP servers, plugins or web tools; remote operations are selected from the app’s fixed diagnostic commands. Runs can be stopped and have a three-minute deadline with at most four model turns.

Codex returns an explanation and proposed port, domain, remote-base, TLS-mode or nginx-config changes. **Apply to form and check** transfers them into the wizard and runs its normal validation. **Prepare server** performs the installation with those inputs and records whether preparation passed or failed. Suggestions alone are marked unverified. The app keeps at most 100 sanitized diagnoses globally and shows the latest 10 for a target; temporary native thread storage is removed when the diagnosis finishes; sanitized app history supplies context for later diagnoses. This integrates the [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk) without giving generated shell commands direct SSH execution.

## Direct GitHub / Ansible

Choose **GitHub → server** and the exact Ansible deployment step. YAML comments are excluded. Build job dependencies are included, while credentials from sibling deployment steps are excluded.

The Strapi/Astro example yields separate development, production UA and production NL targets. Preparation installs Docker, Compose and Python and configures the deploy user and SSH key. GitHub's existing Ansible playbook remains responsible for deploying images and the runtime environment from its vars. The wizard supplies the exact secret names bound to `key`, `inventory` and `known_hosts`, including environment/country suffixes and existing spelling. It does not invent an Ansible Vault password: encrypted vars require their existing password.

Keys shared by several targets in one project are reused and saved before installing the public key on the server. An existing GitHub private key can also be supplied. Credentials and drafts use Electron safeStorage when available. Without a system keyring, they are kept in mode-0600 files inside the app's mode-0700 `deploy-state` directory, like SSH private keys. Env values, TLS private keys and plaintext SSH private keys are never written to `settings.json`. Both profiles provide a separate copy action for the server SSH private key. Passwordless sudo is optional; Docker group membership is provided for Docker operations.

The production playbook in the example uses an external MySQL/MariaDB database. This existing application dependency and its credentials remain in the project's encrypted vars; the app does not silently substitute a new database.

## Results and failure handling

Each completed preparation step is saved. A failure returns the partial result with the SSH key, inventory and known-host entries that are already available; these remain masked and copyable under **Saved credentials and completed steps**. Reopening Deploy Setup selects the most recently saved server and target. Successful results open directly, with **Edit setup** for further changes. Retrying repeats server validation and reuses the saved key and inputs; it does not blindly skip steps based on local history.

Saved status records distinguish incomplete preparation, successful server preparation, certificate issuance/renewal verification and enabled server-pull cron. A prepared GitHub target still requires configuring secrets and running its workflow; server preparation does not claim that GitHub Actions or the application deployment have succeeded. Status reflects the last preparation and is not live monitoring of changes made outside DevScanner.

The first deployment keeps its stdout/stderr in `<remote-base>/run/first-deploy.log`, restricted to mode 0600 and replaced on each attempt. Failure preserves the command’s exit code and shows a sanitized output tail with registry, missing-image, port or health-check hints. Successful output is also shown in progress. Codex’s project-log check reads this file as well as the cron log. Automatic updates remain disabled if the first deployment fails.

After a failed first run, the wizard also reads health status and recent logs for up to four containers belonging to the deployed Compose file, plus bounded responses from up to three configured loopback `*_HEALTHCHECK_URL` endpoints. Requests do not follow redirects or use proxies. Docker may report a healthy process while the deployment readiness endpoint returns 503 because dependencies or required CMS content are missing; these are separate checks. Diagnostic failures never replace the original deployment error. Secret env fields (including individual `APP_KEYS`) are masked; ordinary image names, project names and endpoint URLs remain readable. The wizard does not initialize application content automatically.

Nginx Manager lists `sites-available`, standalone `sites-enabled` files, and the `conf.d/*.conf` files installed by Deploy Setup. Each entry shows its directory and the editor shows its full path. Reads, saves, toggles and deletes use that directory even when another directory has the same filename. Disabling a `conf.d` entry renames it to `.conf.disabled`; it remains editable and can be enabled again. Existing configs open in Raw mode to preserve upstreams, maps, access rules and multiple server blocks when saved. As with other nginx edits, use Test and Reload to apply changes to running workers.

HTTP-only mode preserves the project's access restrictions. If an admin location only allows loopback addresses, a successful localhost check does not prove the operator can open it. Configure the intended operator IPs or VPN CIDRs in the project's nginx allow rules and check access from that network. HTTP-only mode does not configure port 443, certificates, public DNS or NAT forwarding.

The result lists completed steps, installed paths, remaining GitHub secrets/variables, registry instructions and cron status. Instructions and credentials can be copied separately; secret values are masked initially. Remote exit codes are checked. A failed preparation returns the completed steps and does not claim success. Env/Compose validation precedes cron activation. A dedicated existing nginx site for the same domain is updated instead of creating a duplicate. Shared files with unrelated domains are not replaced. nginx is tested before reload; failed configuration restores previous config and supplied TLS files. Changed files retain a `.devscanner-backup` copy. Temporary uploads use a private directory and are cleaned up at the end.

Automatic Docker installation supports Ubuntu/Debian, using the [Docker package repository](https://docs.docker.com/engine/install/ubuntu/#install-using-the-repository). Existing Docker/Compose installations are checked before installing packages. GitHub supplies [`GITHUB_TOKEN`](https://docs.github.com/en/actions/concepts/security/github_token) automatically, so it is omitted from manual secrets. Existing encrypted vars require their [Ansible Vault password](https://docs.ansible.com/projects/ansible/latest/vault_guide/vault.html).

## Verification

`npm test` covers workflow target isolation, env import/quoting, secret mapping, repeated setup, SSH failure paths, nginx rollback, Certbot bootstrap/renewal, Codex cancellation/redaction/history and the renderer flow. A native SDK test uses a local fixture HTTP endpoint with a fake key; it does not call OpenAI. Generated shell scripts are also executed locally with a fake Docker executable to verify pull-before-up behavior and configuration-triggered updates. `npm run build` packages the Electron application. Tests do not connect to production servers, request real certificates or publish images.
